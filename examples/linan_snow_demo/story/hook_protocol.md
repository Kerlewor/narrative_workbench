# Hook Protocol / 伏笔回归机制

本协议用于管理长篇小说中的伏笔、悬念、关系债、设定债和后台真相碎片。核心原则是：**计划中的钩子不是事实，正文写出的钩子才进入伏笔池。**

## Hook 生命周期

| 状态 | 含义 | 可执行动作 |
| --- | --- | --- |
| `candidate` | 规划候选，正文未出现 | 留在 runtime，不进入 `pending_hooks.md` |
| `open` | 正文已经开钩 | 后续章节必须 advance / defer / resolve |
| `progressing` | 正文已经推进至少一次 | 继续推进、升级、回收或延期 |
| `escalated` | 伏笔后果升级，成为更高优先级问题 | 进入核心钩子审计 |
| `resolved` | 正文已经回收 | 写明回收章节与回收方式 |
| `dormant` | 暂时沉睡，但仍保留 | 标明下一次检查章节 |
| `dropped` | 正文主动放弃 | 必须写明放弃原因，避免遗忘式断线 |

## Hook 类型

| 类型 | 用途 |
| --- | --- |
| `前台-悬念` | 明面剧情悬念、任务、追捕、误会 |
| `后台-真相` | 世界观、历史、阴谋、身份秘密 |
| `情感-关系` | 关系进展、误解、亏欠、承诺 |
| `人物-弧光` | 角色缺陷、选择债、成长节点 |
| `物件-证据` | 道具、证据、伤痕、文件、信物 |
| `环境-状态` | 社会局势、灾害、战争、公共认知 |
| `主题-回声` | 意象、台词、场景回环 |

## Hook 字段定义

`pending_hooks.md` 必须使用以下字段：

| 字段 | 说明 |
| --- | --- |
| `hook_id` | H001、H002 等稳定编号 |
| `起始章节` | 正文首次成立的章节 |
| `类型` | 使用 Hook 类型之一 |
| `状态` | 使用生命周期状态之一 |
| `优先级` | core / high / normal / low |
| `最近推进` | 最近一次在正文中被推进的章节 |
| `预期回收` | 应回收的事件、答案或情绪节点 |
| `回收卷/章` | 预计在哪卷或哪章回收，可为空 |
| `回收节奏` | 立即 / 近期 / 中程 / 慢烧 / 终局 |
| `上游依赖` | 必须先解决的 hook_id |
| `半衰期` | 允许不触碰的最大章节数 |
| `升级条件` | 什么情况下升级为 high/core |
| `正文证据` | 开钩或推进时的正文依据 |
| `备注` | 额外说明 |

## 半衰期规则

半衰期是“允许不碰这个钩子的章节跨度”。

| 回收节奏 | 建议半衰期 |
| --- | --- |
| 立即 | 1-2 章 |
| 近期 | 3-5 章 |
| 中程 | 6-12 章 |
| 慢烧 | 13-30 章 |
| 终局 | 每卷至少推进一次 |

如果 `当前章节 - 最近推进 > 半衰期`，写下一章前必须执行以下三选一：

1. 本章推进它（advance / escalate / resolve）。
2. 明确 defer，并写出延期理由。defer 是本章级动作，不改变 hook 状态——hook 保持 open/progressing，仅跳过本轮半衰期检查。连续 defer 同一 hook 超过 3 次视为事实上的 dormant。
3. 判定为 dormant / dropped，并写明原因。dormant 时在备注中标注下次检查章节（如"Ch15 时重新评估"）。

## 活跃钩子预算

- 活跃钩子总量建议不超过 15 条。
- `core` 钩子建议不超过 5 条。
- 每章最多新开 1-3 条钩子。
- 优先回收旧债，再开新坑。
- 同一章尾不能机械重复同一种钩子。

## 单章 Hook 操作

每章 intent 必须填写：

```text
open:
- [new] Hxxx ... || 正文证据预期：...

advance:
- [advance] Hxxx ... || 推进方式：...

resolve:
- [resolve] Hxxx ... || 回收方式：...

escalate:
- [escalate] Hxxx ... || 升级条件触发：... || 新优先级：...

defer:
- [defer] Hxxx ... || 延期理由：...
```

每章写定后，主会话只根据正文真实出现的内容更新 `pending_hooks.md`：

- 正文没有写出的 `open` 不能进入伏笔池。
- 正文没有推进的 `advance` 不能更新“最近推进”。
- 正文没有明确回答或情绪闭环的 `resolve` 不能标记 resolved。

## 批量 Hook 审计

批量写作前必须做 hook 预算：

- 本批要回收哪些旧钩子。
- 本批必须推进哪些半衰期即将到期的钩子。
- 本批允许新开几个钩子。
- 哪些核心真相禁止提前掀开。

批末 audit 必须检查：

1. planned hook 是否真的出现在正文。
2. `pending_hooks.md` 是否错误吸收了 candidate。
3. 是否有半衰期到期未处理的 hook。
4. 是否存在 resolved 但正文没有回收证据的 hook。
5. 是否有过多新钩子导致活跃钩子超预算。

## 回收质量标准

一个 hook 只有满足以下至少两项，才算合格回收：

- 读者得到明确答案或明确情绪结果。
- 角色状态发生可见变化。
- 上游或下游 hook 被连带推进。
- 相关物件、台词、场景意象完成回环。
- 回收后产生新的不可逆局面。

单纯“解释一下发生了什么”不算高质量回收。
